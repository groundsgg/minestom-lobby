# Per-viewer NPC delivery on shared serialization

Continue N13 on accepted main `83e1fba` (#237), after the user confirmed Stage scale and SOLID. #233, #236 and #238 stay independent. Standing instructions authorize sensible implementation, tests and qualified Stage activation without repeated design questions.

Current main samples one shared pose at the nearest viewer's 200/250/500 ms rate and sends it to every viewer. #233 accumulated cohort deltas but filtered every display's complete viewers collection for every cohort and serialized individually per recipient, alongside instrumentation and renderer-math changes. Its CPU regression prevents deployment as-is.

Selected approach: isolate cohort delivery/lifecycle correctness, keep the current renderer math and cadence, group candidate recipients once per handle membership/rate revision, and use the accepted native shared serialization for identical recipients within a cohort. Check actual display membership before sending; a candidate viewer without a spawned display must not receive deltas. Use enum rate identities, not freshly boxed per-player millisecond values. Keep bounded accumulators (at most three per display) and immutable ownership when packets are queued. Entry, rate changes, start/stop/seek and personal scale require coherent full state with the recipient's interpolation duration; a highlight alone must not flush pending pose changes. Joining an occupied group must not postpone other viewers' deadlines. Dropped groups and close release pending state. Near/mid/far admission uses the existing 64/72 block range plus vertical32, with rate hysteresis 16/18 and32/36 blocks as in the old tested draft. All body parts still update together; animation time remains real elapsed time.

Alternatives: merge #233 wholesale (reject: mixes previous CPU regression, instrumentation and unrelated math); implement versioned field arrays immediately (defer: first measure whether fixed recipient grouping and native caches suffice); reduce render distance or geometry (reject: conflicts with accepted visuals). This is the agent's engineering choice under the user's instruction to continue.
